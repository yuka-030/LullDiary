# データベース設計

## 保存方針

SQLiteに日記の情報を保存し、写真と読み上げ音声はファイルとして保存する。

元の録音音声は永続保存しない。文字起こし時の音声は一時ファイルとして扱う。

## 保存場所

```text
apps/server/app_data/
  db/
    lulldiary.db
  narration/
    {日記ID}.wav
  photos/
    {日記ID}/
      photo1.jpg
```

SQLiteの動作により、データベースの補助ファイルが作成される場合がある。

## entries

| カラム         | 内容                                     |
| -------------- | ---------------------------------------- |
| id             | UUID形式の日記ID                         |
| created_at     | 作成日時                                 |
| input_type     | voice または text                        |
| raw_input_text | 確定した入力文                           |
| story_text     | 生成・編集した物語文                     |
| narration_path | 読み上げ音声の保存先。音声がなければnull |
| tags           | シーンと感情を含むJSON                   |
| photo_paths    | 写真の保存先を含むJSON配列               |

JSONはデータベースでは文字列として保存し、APIで使用するときにオブジェクトや配列へ変換する。

`photo_paths` は配列の形式だが、現在の写真添付は最大1枚とする。

スキーマの変更はマイグレーションで管理する。元の録音音声の保存先を表す `recording_path` は現在のスキーマに含めない。

## 作成

入力方法、入力文、物語文、タグ、添付ファイルを検証して保存する。

テキスト入力の場合は、サーバー側でも120字以内か確認する。音声入力の認識結果には、この120字制限を適用しない。

## 取得と絞り込み

- 一覧を取得できる。
- IDで1件取得できる。
- 年月、シーン、感情を条件にできる。
- 複数の感情を指定した場合は、指定した感情をすべて含む日記を返す。
- 作成日時の降順で取得する。

SQLへ渡す値はパラメーター化し、ユーザー入力をSQL文へ直接連結しない。

## 更新

物語文、タグ、読み上げ音声、写真の更新に対応する。

写真は差し替えと削除ができる。不正な入力や添付ファイルを保存前に検証する。

データベースとファイルは別の保存処理であり、両方をまとめた単一のトランザクションではない。

## 削除

日記の削除に合わせて、紐づく写真と読み上げ音声を削除する。

正常な削除でデータベースとファイルが残らないことを、結合テストで確認する。

## 写真

- 最大1枚
- 入力はJPEG・PNG・WebP
- アニメーション画像は対象外
- 最大20MiB
- 最大6400万画素
- 向きを補正
- 縦横比を維持し、長辺を最大1000pxへ縮小
- 小さい画像は拡大しない
- 透過部分を白で合成
- JPEG品質80で保存

独立したサムネイルは作成せず、縮小した保存画像を使用する。

## 音声

保存する読み上げ音声はWAVとする。

- 最大20MiB
- PCM 16bit
- モノラルまたはステレオ
- サンプリング周波数は8〜96kHz
- WAVのヘッダーとデータ構造を検証

アップロード全体の上限は41MiBとする。

## ファイルの配信

日記IDと対象ファイルを検証し、所定の保存先にあるファイルを配信する。

任意のパスを指定して読み出す構成にしない。配信時は形式に対応するContent-Typeと、`X-Content-Type-Options: nosniff` を付ける。

## テスト用データ

結合テストとE2Eテストでは、通常のアプリとは別のデータベースと保存先を用意する。

テストデータの初期化と後片付けは、通常の日記データへ影響しない範囲で行う。
